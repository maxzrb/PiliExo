## 已修复的问题

### 1. 高优先级：FFmpeg 私有选项误当 mpv 顶层选项

原 JNI `metadata` 对 `piliexo_dolbyvision`、`piliexo_metadata_callback`、`piliexo_metadata_opaque` 调用 `mpv_set_option_string` 并忽略返回值。补丁只在 FFmpeg MediaCodec 解码器的 AVOption 表注册这些名字；mpv 不会自动将未知顶层选项转发给解码器。结果是选项传递失败，动态回调/杜比解码配置无法按预期启用。

修复：JNI 返回会话解码参数，经 Kotlin create 结果交给 Dart，每次打开媒体时与现有 `operating_rate` 合并到 `vd-lavc-o`。旧插件未返回参数时明确初始化失败，沿现有回退流程处理。媒体缓存及其他 extras 保留。

回调真正启用后，解码线程可能晚于输出释放才回调，原来的裸 `Output*` 会产生释放后访问风险。本轮一并改为递增令牌和持有共享引用的接收端注册表：释放先注销，再等待正在执行的回调完成后删除 JNI 引用；迟到回调直接忽略。

### 2. seek 的空载荷 flush 与 Kotlin 非空参数冲突

FFmpeg flush 明确传入 `type=0/data=NULL/size=0`；JNI 同样传空数组引用，但 Kotlin 原来声明 `ByteArray`，会在进入清理分支前抛异常，JNI 又将异常清除，队列未被清理。

修复：参数允许空值，flush 清空队列、静态元数据和当前段计数；非 flush 空载荷忽略。固定输入覆盖 flush、迟到空载荷与 seek 后新元数据。

### 3. 复用原生会话时只比较 Codec String

原切源判断只比较是否原生和 codecs，未比较 `qualityCode`、源宽高和硬解设置。普通 HDR 与 Vivid 使用相同 HEVC codec 时会复用未创建 Vivid 管线的旧会话；已有 Vivid 管线也可能沿用旧尺寸。

修复：将原生会话配置与新源完整比较，配置变化时走既有释放/重建流程。

### 4. 长度前缀被误认成 Annex B 起始码

旧解析器在整个包中搜索 `00 00 01`，任何匹配都会跳过长度前缀解析。已用长度为 256 的合法 SEI NAL 复现：四字节长度 `00 00 01 00` 被误认为起始码，预期一条 Vivid 元数据，实际输出为空。

修复：输入格式由调用者明确给出；0 为 Annex B，1～4 为长度字段字节数。长度包先完整校验再回调，损坏的尾部不会产生部分副作用。

适用边界：FFmpeg HEVC MediaCodec 自带 `hevc_mp4toannexb` 位流过滤器，生产调用明确使用 0。本例证明旧解析工具宣称支持的长度前缀路径有误，不据此宣称已在真实 MediaCodec 播放中复现同一现象。

### 5. 正式核心的构建清单缺失动态 HDR 补丁

两个正式 APK 中的 libmpv 含动态 HDR 选项字符串，而 `sources.json` 没列入 `ffmpeg-android-dynamic-hdr.patch`，README 又称 FFmpeg 使用基线，无法按清单恢复所需实现。

修复：将动态补丁及 SHA-256 列入正式 `patches`，静态元数据研究补丁继续保留在 `researchPatches`。新增 `tool/prepare_mpv_sources.py` 校验补丁身份、顺序应用正式补丁并检查已应用状态；已在从旧补丁还原的 FFmpeg 基线上实际应用和复查成功。此工具负责源码准备，不替代完整依赖构建、打包和设备验收。
