# 官方 B 站 Android 长按倍速实现调查（2026-10-19）

调查对象：本机官方粉版 tv.danmaku.bili 9.15.0 / 9150300，HONOR NTH-AN00 / Android 14。用户要求先调查官方逻辑，本轮没有修改 PiliExo 播放代码、构建、安装或发布。

## 结论

官方长按流畅不能只归因于降分辨率，也不能用一个 framedrop 参数概括。当前 APK 的旧 IJK 调用链包含：按实验/片源确定临时倍率、异步设置速度、原生再次限制倍率、动态提交硬解 operating-rate、压缩包阶段跳过落后的非参考帧、解码输出阶段按主时钟丢帧、松手撤销临时速度。

尤其需要修正比较条件：该原生链在视频元数据帧率达到 50fps 时返回最高 2 倍，上层请求 3 倍也可以被钳制。不能把官方仅显示“倍速中”的测试直接当成与 PiliExo 明确 3.0 倍等负载。

以下“默认值”指当前 APK 中的代码默认值，实验/业务可以覆盖；“存在分支”不等于每次采样均已确认命中。

## 1. 手势和临时速度

Theseus 普通详情页的 `com.bilibili.ship.theseus.united.player.e` 在构造时启动 `TripleSpeedService$runOldTripleSpeed$1`，注册长按监听。开始时检查处于可播放状态、没有旧长按任务，然后读取当前媒体，调用 `com.bilibili.playerbizcommonv2.utils.C.b(mediaResource)` 计算倍率。

`LongPressSpeedExperiment` 有六组：

| 实验 | C.b 返回的长按请求倍率 |
| --- | --- |
| TripleSpeed | 3.0 |
| Speed1_5 | 1.5 |
| Speed2 | 2.0 |
| SmartLongPress | scriptPace >= 5 时 1.5，否则 2.0 |
| SmartLongPressAnd3x | 同上；3 倍选择的开放另有判断 |
| Speed2And3x | 2.0；3 倍选择的开放另有判断 |

智能组读取业务附加字段 `united_player_script_pace`，并回退读取 archive info 的 `scriptPace` / `script_pace`。这不是实时检测解码压力后得出的倍率。

同一工具类生成倍率菜单时，还会按所选流帧率判断 3 倍入口能否使用：`C.c(fps)` 要求 fps > 0 且 fps < 50；实验组和是否 downloaded 也参与判断。不能把界面有没有“3 倍”只归于会员或手机性能。

`PlaySpeedManagerImpl` 把基础速度与临时速度分成两个 StateFlow，合成时优先使用非空的临时值。长按协程设置临时值并等待取消；松手取消任务，清除临时值，回到原基础速度。复杂协程的普通 JADX 输出存在语句重建错误，已经用 `speed-manager-simple.java` 的线性指令复核设置/清除顺序。

速度沿播放器服务进入 `IjkMediaPlayAdapter` 的 `OpSwitchSpeed`，调用 `IjkMediaPlayer.setSpeed(float)`；后者发送异步消息 `what=16, arg1=10003`，工作 Handler 再执行 `setPropertyFloat(10003, speed)`。这条速度设置路径没有把每次长按实现为重新打开视频或一次 seek。

## 2. 原生层再次限制倍率

当前 APK 的 `libijkplayer.so:ffp_set_playback_rate` 位于 RVA `0x3a5e4`。它先调用 `GetAICenterOutput(9, ..., itemId)` 取得最大允许速度；请求高于上限时，打印钳制日志并用上限替换请求，然后保存实际速度、速度变化标志和给 AICenter 的当前速度输入。

`GetAICenterOutput(9)` 位于 `libijkffext.so`，其分发表转入 `0x1eb9b8`，随后调用 `0x1ee0a0`，日志名称为 `GetMaxPlayRate`。还原结果为：

```text
若元数据 fps >= 50：maxRate = 2.0
否则若 enhance 标志为真：maxRate = 2.0
否则若命中软件 VVC 分支：maxRate = 2.0
否则：maxRate = deviceMaxPlayRate（该库初始值为 3.0）
actualRate = min(requestedRate, maxRate)
```

fps 字段不是凭偏移猜测：`update_ijkmeta` 在 `0x3fde4` 调用 `ijkmeta_get_fps_l`，写 FFPlayer+0x1484，再以 `SetAICenterInputWithVarargs(6, itemId, fps)` 进入 ItemInfo 首个 double；最大倍率函数正是读取该字段与 50.0 比较。

增强标志也已追到 Java：`IjkMediaPlayerItem.setEnhanceQnList` 在列表非空且 `AbrParamsInterface.IsEnableVodEnhance()` 为真时设置 item property 15；native 将其转成 AICenter 输入 12，保存为上述布尔字段。本机该远端增强开关未直接读取，不能宣称必然命中。

另外有降低后续最大倍率的保护：原生记录解码耗时和当前播放倍率，在低于 50fps、设备上限仍为 3、当前倍率为 3 等条件下，累计解码过慢达到约 2 秒，可将 deviceMaxPlayRate 改为 2。代码日志为 `videoDecSlowDuration ... decrease deviceMaxPlayRate`。这证明上限可以变化；尚未证明写入上限的这一刻就同步把已经播放中的速度降为 2，因此不做这个额外推断。

## 3. 解码前和解码后分别减负

Java `IjkMediaConfigParams` 的默认 `mEnableDropFrame=true`、`mEnableEarlyFrameDrop=true`、`mSkipFrame=0`。`IjkMediaPlayerItem.setItemOptions` 分别写：

- 播放器选项 `framedrop=1`（当 mEnableDropFrame 为真）；
- Codec 选项 `skip_frame=mSkipFrame`，默认 0；
- item 选项 `early_framedrop=1/0`；
- 普通点播 `high-fps=1`，直播 `high-fps=0`。

取帧或 raw data 模式会设置 recording，并把 framedrop 与 early_framedrop 两种开关关掉。这些是会话初始化的能力/策略，不是发现一个长按手势后才临时打开、松手就必然全部关闭。

### 压缩包阶段

`libijkplayer.so:do_early_drop_packet` 位于 `0x49b88`。它检查 early_framedrop 开关、队列序列、包时间与主播放时钟的关系，并对 H.264/HEVC 等路径解析 NAL、调用 `ijk_h2645_nal_is_no_ref`；符合条件的非参考包可以提前标记跳过。

这一层可以少送一些无须保留的压缩视频包去解码，同时保留参考关系。它与“把所有视频包任意隔一个扔一个”不同，也不等同于 mpv 设置一个同名选项就能获得完全相同的 MediaCodec 行为。

### 解码输出阶段

`is_need_drop_frame` 位于 `0x49e54`。它比较当前帧 PTS 与主时钟、检查有效时间差/序列及队列余量，并限制连续丢帧次数。连续满足落后条件且 `framedrop=1` 时，其计数分支会丢一帧后至少放过一帧；不是要求永远把所有过期帧逐帧呈现。

MediaCodec 路径在 `0x34ae8` 调用该函数；命中后释放 buffer proxy / AVFrame，未命中才进入 `ffp_queue_picture`。因此这部分减负发生在向画面队列提交之前。后续呈现/时钟同步还有其他逻辑，本轮没有把所有显示线程分支穷尽。

这与实测中 Rendered 和 Discarded 各约一半相容，但尚不能把每一条厂商 TraceLog 丢弃逐项归属到某个 native 分支，也不能声称官方固定锁定 30fps。

## 4. 动态设置 MediaCodec 解码需求

这是与 PiliExo 当前“打开视频时预留一次需求”值得单独比较的一点。

普通点播的 high-fps item 字段复制到 FFPlayer 后，MediaCodec 输入线程在开关开启、Android API >= 23、有效 Codec 存在、当前倍率 > 0.01 且与上次提交倍率不同等条件下，创建 Bundle，写入 float `operating-rate`，调用 `SDL_AMediaCodec_setParameters`。定位为 `libijkplayer.so 0x3535c–0x35458`；成功后记录已提交倍率。

计算 helper `0x33c48`：先 `av_guess_frame_rate`，失败时用 30；倍率 <= 1.01 按 1 计算，随后将 fps × rate 限在 [15,240]。这是解码器吞吐提示，不是强制屏幕以该帧率显示，也不是这台硬件一定能达到的性能承诺。

它使用运行中的 setParameters，已定位的这段代码没有为切倍速执行 Codec configure/重建。该路径是否在每一次测试切速成功生效，仍需运行时参数或调用证据；不能仅凭代码推算实际功耗收益。

`max-fps` 选项表默认 61，说明文字针对源视频帧率过高；不能把它解释为“长按固定送显 30 帧”。

## 5. 运行记录及明确边界

此前已绑定实际输出格式的有效 4K 长按窗口，来自 `matrix-edges-logcat.txt`：20:02:39.430 输出 3840×2160，20:02:54–20:03:04 长按。20:02:55–20:03:03 共 9 个统计点，Done 中位 62.9/s、Rendered 31.0/s、Discarded 31.7/s，期间无降低尺寸输出事件。该轮不是零丢弃。

本轮补采 `speed-runtime-valid`，同 BVID、基础倍率菜单为 1.0、控制栏为 4K，截图确认“倍速中”：

| 窗口 | 样本数 | Codec Done 中位/s | Rendered 中位/s | Discarded 中位/s |
| --- | --- | --- | --- | --- |
| 长按前 20:41:44–54 | 10 | 39.35 | 19.7 | 19.85 |
| 长按前段 20:41:58–20:42:05 | 7 | 62.8 | 30.9 | 31.9 |
| 松手后 20:42:10–20 | 10 | 61.2 | 59.9 | 0 |

必须同时保留不利结果：20:42:07.282 出现 `Render jank? last 121005972 now 121008378`，即约 2406ms 的 Codec 送显间隔；不能把前段统计当作整段均无停顿。该窗口不能分辨网络等待、解码等待和其他原因，不直接归因。

这次新采集起点没有包含该 Codec 的输出格式变化事件，日志环形缓冲也已覆盖早期事件，所以新一轮的“4K”只是界面条件，不单独提升为实际尺寸证明；严格的 4K 结论仍依据上一段包含 crop 的有效日志。长按前已存在丢弃，也不能说所有丢弃都由长按新触发。

MediaSession 的 position/speed 在这版里没有逐帧刷新，长按时仍可能留着旧的 speed=1.0；本轮没有把它当作真实倍率测量。截图从长按前 02:59 到结束后 03:20 跨约十几秒、期间还有输出间隔，不足以精确确认实际 1.5/2.0/3.0；原生的倍率钳制属于直接代码证据，运行时实际倍率仍需独立 PTS/播放时钟采样。

`speed-runtime` 第一轮没有真正恢复播放，截图/MediaSession 一直停在 02:13，未出现 Codec 统计；整轮排除。保留原始文件，防止误用。

上述 Rendered/Discarded 是 Codec 输出释放统计，不是最终屏幕 FPS。没有据此计算功耗、得出整机性能排名或声称官方永远不卡。

## 6. 对后续修改的约束（尚未实施）

不能直接把“官方 4K 倍速流畅”作为让 PiliExo 完整呈现 4K60×3 的等价目标。先确定目标倍率与是否接受跳过过期画面，再选择实现：

1. 保留基础速度/临时速度分离，以及松手不等待旧命令回复；这是两边已经相似的部分。
2. 若要实现官方式高负载快进，重点在参考关系安全的解码前减负和解码输出前的过期帧释放，避免积压。不是仅修改 Dart 层 framedrop 字符串就宣称已复刻。
3. 硬解运行需求要覆盖源帧率与实际倍率；官方有运行中更新 operating-rate 的链，PiliExo 现有预留策略需按同一片源核对后再决定是否改动。
4. 若选择倍率上限或主动抽帧，必须在产品行为上明确，不沿用“3 倍请求”却把降低后的负载当成完整 3 倍性能。不能为了洞察变成零丢帧而隐藏实际丢帧。

本轮仅给调查结果，不实施上述任何改动。
