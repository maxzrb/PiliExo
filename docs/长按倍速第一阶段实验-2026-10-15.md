# 长按倍速第一阶段实验（2026-10-15）

## 当前结论

在 NTH-AN00 老手机的固定 1080p60 HEVC 视频片段上，带 `operating_rate=180` 的实验包表现出稳定且显著的改善：长按期间 Codec Done 约180帧/秒、送显约179帧/秒，播放器报告的位置推进约3倍，音画偏差P95为3～25毫秒；松手后稳态观察窗口送显恢复约60帧/秒。

同源码、不覆盖运行速率的包重复三次均降至约9帧/秒送显，松手后20秒观察期仍在追帧。切换为 audio 同步模式也没有解决。换回无参数包的一次反向复测再次出现同样问题，降低了素材差异、单次缓存和偶发状态造成结果的可能性。

这足以把解码运行速率列为首要实施方向，但尚未完成生产验收：**实际呈现间隔、150ms以内切换延迟、8e适配和等流畅度的功耗对照仍待验证。** 补采CCodec/CCodecConfig的DEBUG级日志后仍提示没有 operating-rate；mpv属性已读回实验值，但原生参数的最终接收位置仍未证实。不能将结果写成已证明驱动收到180或已经找到唯一根因。

## 1. 实验条件与控制变量

- 设备：HONOR NTH-AN00 / SM7325 / Android 14，屏幕1080×2340，调查时显示模式120Hz；不是8e。
- 应用：包名 `com.maxzrb.piliexo`，versionName `26.10.14`、versionCode `29`，同一正式签名覆盖安装，保留数据。未发布、未修改项目版本。
- 视频：`BV1a2pr6aEC1`，cid `42725214122`，《【胡闹战地】最好的老师-10发M417》，1080p60 HEVC；原生日志均使用 `c2.qti.hevc.decoder`。
- 每轮强停后冷启动同一链接，从60秒开始，等待音频时钟存在且进度连续推进，再正常播放8秒、按住10秒、松手恢复20秒。
- 用户原配置为 `video-sync=display-resample`；audio对照完成后已恢复。画质、音频输出、弹幕和界面保持原有配置。
- 无参数包与180包使用相同应用源码、相同锁定依赖和相同原生libmpv/libflutter二进制；构建参数分别为0和180。两者均启用相同时序诊断。
- 先前 `baseline/` 的三轮试跑使用较弱起播判断，包含初始seek追赶，不纳入主表。主表采用修正判断后的三组三轮，另列一次反向复测，共10轮。
- Flutter/Android构建目录先后位于D盘工程和本机C盘隔离克隆。后者用于避开百度网盘向AAPT资源目录写入 `.baiduyun.uploading.cfg` 导致的构建失败；没有关闭同步程序或删除用户文件。

### 指标边界

1. Codec Rendered表示向Surface释放的帧数，**不等于物理屏幕真正呈现的帧数**。120Hz屏幕不会显示180张不同画面/秒；目前不能宣称“屏幕达到179fps”。
2. `speed`为原生配置值，位置推进由播放器位置/墙上时间计算。当前mpv没有提供可用的 `video-pts`、`mistimed-frame-count`，结果保留null；没有编造真实视频PTS。
3. 500ms采样和约1秒Codec统计适合识别持续追帧，不足以判定松手后首帧是否在150ms内呈现。主表剔除了阶段首约1.5～2秒和尾0.5～1秒，也不能用稳态结果代替瞬时切换结果。
4. 同步FFI属性读取有观测开销：无参数组长按时每轮queryUs的P95约53～105ms，180组约10～27ms。原始未加本轮诊断的应用已出现约9帧/秒，故不能把持续异常全部归因于采样；实际手感和功耗验收必须使用关闭诊断的Release包。
5. 起播source事件早于解码器初始化，hwdec为空、fps为null，不能据此判断软解。硬解以随后CCodec组件和实际吞吐日志为依据。

### 重连后的补充确认

- `operating-rate-180-confirm/`：按原坐标执行，但没有gesture_start/gesture_end，且hold窗口始终为1倍速，因此该轮无效并排除。原始日志保留用于审计，不能将正常60帧误当成3倍速成功。
- `operating-rate-180-ui-confirm/`：用户授权从观看记录进入同一视频，在已核对布局的当前页面接入，使用 `(800, 450)` 进行长按；捕获到完整3→1请求及确认。由于起点约140秒，作为补充确认，**不并入从60秒开始的主表**。
- 有效补测：长按Done179.79、Rendered177.79、Discarded2.14帧/秒；位置推进2.996倍，avsync P95为10.718ms。恢复阶段Rendered60.00、位置推进0.99996倍、avsync P95为0.340ms。长按/松手回执分别约0.980/0.595ms，仍不能代替屏幕呈现延迟。
- 电池温度36.9→37.3°C，Thermal Status均为1，USB充电；仅短时单轮条件记录，不作为省电或热安全验收结论。
- 补采CCodec DEBUG配置仍无operating-rate接收证明；初始缺失日志不能被解释为已经确认收到180。
- 回查主表9轮、反向1轮及新补测1轮的手势与配置速度均通过，另1轮无效。结果保存在 `validation-audit.json`；脚本已加入相同校验，失败时保存数据并停止后续轮次。

## 3. 已实现的第一阶段代码

- 新增 `PlaybackRateCoordinator`，区分用户基础速度、长按临时速度和后端确认速度。仅保留尚未执行的最新请求，迟到回执不覆盖新手势；旧请求失败后仍执行最终恢复目标。
- 切源使用generation隔离，旧后端未完成请求不阻塞新会话。暂停、完成、锁定控制和应用进入后台时结束临时加速；基础1.5倍速等设置可以可靠恢复。
- 新增构建开关与时序记录器，记录手势、命令下发/回执、位置/音频时钟、音画偏差、丢帧和Flutter耗时。默认构建不启用诊断，也不覆盖运行速率。
- `PILI_PLAYBACK_DIAGNOSTICS` 与 `PILI_MPV_OPERATING_RATE` 后续已拆为独立开关，允许关闭诊断、保留相同速率参数做功耗测试。已采集两个APK均启用诊断，此调整不会改变它们对应的实验行为；现有APK尚未重建包含这次独立开关调整。
- ADB脚本保存分轮UTF-8原始日志和JSON统计，等待真正起播，结束时强停应用。补充轮次前后的电池/热状态记录；设备断连时清理失败不应覆盖原始错误。轮次前后上下文采集已在补充复测中成功运行。

## 4. 功耗反馈核对与约束

用户提出的PiliPlus历史功耗问题已找到对应原始反馈，以下是问题线索，不是经过统一控制变量的功耗测量：

- [#2411 安卓异常耗电](https://github.com/bggRGjQaUbCoE/PiliPlus/issues/2411)：报告播放时CPU频率变化和电流峰值较高；关闭原因为not planned，不能解释为修复完成。
- [#2814 后台耗电](https://github.com/bggRGjQaUbCoE/PiliPlus/issues/2814)：Redmi KPad用户报告不播放、划掉后台后仍耗电，另有相似跟帖。需要单独检查资源释放，不能用前台解码参数解释全部现象。
- [#2832 持续120帧诉求](https://github.com/bggRGjQaUbCoE/PiliPlus/issues/2832)：发帖者补充为iPhone14Pro；安卓跟帖提到刷新率选项。该讨论不能证明本机弹幕是功耗根因，也不直接照搬降低帧率方案。
- [#1320 自适应刷新率诉求](https://github.com/bggRGjQaUbCoE/PiliPlus/issues/1320)：仅有功能诉求，缺少可用的定量验证。

### 优先消除无效工作，保持画面与交互流畅

1. **解码需求按素材与倍速规划。** Android将operating-rate用于资源规划和运行点选择；180是60fps×3的实验值，不能推广为全部素材的常驻固定参数。[Android MediaFormat](https://developer.android.com/reference/android/media/MediaFormat#KEY_OPERATING_RATE)
2. **优先研究运行中更新需求。** 当前FFmpeg选项在解码初始化写入format；动态更新需要确认mpv/FFmpeg本机实现是否提供不重建Codec的接口，再评估原生桥接。禁止每次长按重建解码器。若当前库不支持，先比较较低但能稳定满足需求的初始化值及实际常速功耗。[FFmpeg MediaCodec源码](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/mediacodecdec.c)
3. **减少不可见渲染与同步读回。** 洞察HUD隐藏时仍可能随快照setState；竖屏环境效果约每次截图耗时加66ms采样一帧。后续分别对照，优先缓存、跳过无变化/不可见工作。不能随意冻结正在观看的背景效果后称为无损省电；本轮未改这些行为。
4. **停止闲置任务。** 暂停/退出/听视频/切后台分别确认视频解码、ambient截图、HUD、Ticker、定时器、音频会话与wakelock是否符合功能状态。听视频仍需要音频，不能简单把后台服务全部杀掉。
5. **只处理无法呈现的额外工作。** 60fps×3超过120Hz时，研究在昂贵的GPU处理之前规律跳过无法显示的帧，同时保留显示刷新与时间轴节奏；Codec送显179不意味着这些帧都有效呈现，也不保证减少这部分就能减少依赖帧解码成本。须用实际呈现数据证实。
6. 不改为全局30/60帧上限，不用不均匀抽帧换电量数字，不默认降低画质/倍速或关闭弹幕。滚动、拖动、倍速手势和弹幕平滑度需要同时验收。

### 不重建解码器的动态需求：已找到可参考实现

本项目实际依赖Media3 1.11.0。核对该**相同版本**的源码，视频Renderer按已知流帧率与目标倍速的乘积计算operating-rate，通用Renderer通过 `Bundle.putFloat(MediaFormat.KEY_OPERATING_RATE, ...)` 和 `codec.setParameters(...)` 在运行中更新；这条更新路径不要求每次变速重建Codec。[1.11.0视频Renderer](https://github.com/androidx/media/blob/1.11.0/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/video/MediaCodecVideoRenderer.java#L1522)，[1.11.0参数更新](https://github.com/androidx/media/blob/1.11.0/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/mediacodec/MediaCodecRenderer.java#L2019)

这为60→180→60的需求切换提供了可核对的工程参考。mpv当前使用的libmpv/FFmpeg二进制尚未确认有等价公共控制接口；不能从Dart保存的speed直接取得内部MediaCodec实例，也不能仅在Java侧另建一个Codec后期望影响mpv。若需维护自定义FFmpeg/native补丁，应评估库构建、线程归属、切源、驱动兼容和更新成本。FFmpeg上游公开的mediacodec.h与wrapper目前没有可直接照搬的setParameters公共入口；上游master不等于本机二进制的精确实现。

因此下一步并列比较：保留mpv的小范围参数方案能否通过常速功耗验收，以及复用现有Media3作为可选SDR实验路径的成本。当前没有改变后端选择规则，也没有因180包改善就提前承诺固定参数或全面迁移。

### 当前不能给出省电百分比

设备通过USB充电，长时间连续实验后曾读到电池37.7°C、Thermal Status=2；调查早期约31.8°C、热状态0。多项实验、充电和时间顺序共同变化，没有逐轮温度配对，不能归因于180参数，也不能证明无额外发热。充电电流、电量变化和CPU频率均不能直接当作整机功耗。

正式功耗对照使用关闭诊断的Release包，固定亮度、分辨率、编码、网络、音量、弹幕和实际刷新率；每组从相近温度开始，采用A/B与B/A顺序，各持续10～15分钟并重复。优先断开USB后用无线ADB或外部测量，明确设备电流单位、方向及电量计能力，同时保存温度、热状态、实际帧间隔和音画同步。没有可用能量计时，只报告资源/热状态代理指标，不输出瓦特或省电比例。

验收以同等流畅度为前提：常速无持续额外负担，松手迅速恢复，长按实际速度不掉队；实际呈现间隔P95/P99和长空档不得恶化。功耗下降但新增低帧率卡顿，不接受。
