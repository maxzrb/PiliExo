# mpv 原生 HDR 迁移与 Dolby Vision Profile 5 验证

> 2026-11-10 后续更正：15:55 的峰值判断未获同帧验证；460 nit会触发mpv内部映射。最新候选保留PQ/HLG信号，并补EGL静态元数据，实际替换配套核心。以下为早期阶段记录，最终实现与验证边界以 [偏灰修正报告](mpv-HDR偏灰修正与数值回归-2026-11-10.md) 为准。

## 当前状态

2026-11-10 在 `codex/mpv-native-hdr` 分支实现实验性原生输出，默认关闭。沿用正式版 mpv 核心和音频策略，增加独立 SurfaceView、NativeWindow dataspace 桥接与 P5 软件解码策略。arm64/v7 双 ABI 已本机构建，arm64 已在真机通过 HDR、P5 和覆盖层验收；这不是正式发布，也不代表全设备、全部 HDR 格式通过。

## 为什么 PiliPlus 没有直接使用 mpv HDR

PiliPlus 的 [HDR issue #434](https://github.com/bggRGjQaUbCoE/PiliPlus/issues/434) 标记为依赖问题并关闭。[维护者回复](https://github.com/bggRGjQaUbCoE/PiliPlus/issues/434#issuecomment-2717631563) 引用了 [PiliPalaX 的说明](https://github.com/orz12/PiliPalaX/issues/203#issuecomment-2313866409)，意思是当时采用的播放器无法支持，暂时没有解决办法。没有证据表明维护者是出于画质或性能偏好主动拒绝现成可用的 mpv HDR。

[media-kit #573](https://github.com/media-kit/media-kit/issues/573) 讨论了 Android 原生 mpv HDR 的缺口、SurfaceView 与 gpu-next/libplacebo 的关系，以及当时构建缺少 libplacebo 的情况。这是历史依赖背景，不能据此断言今天所有 mpv 构建都不能处理 HDR 或 Dolby Vision。

本轮只读核查的 PiliPlus `upstream/main=2dd24225b`，仍使用 media-kit 的普通 Android SurfaceTexture 视频输出，未配置本轮的 gpu-next、10位 EGL 和 PQ dataspace 路径。此引用更新不代表本地合入了该提交之后的上游功能。

## 与 Hills 的关系

Hills 已安装 APK 的调用和二进制证据表明，它使用原生 SurfaceView、gpu-next 和定制 Android HDR probe，调整 NativeWindow BT.2020/PQ dataspace 并回读检查。相关日志明确写着没有 HDR metadata，不能将其等同于完整 Dolby Vision 或 HDR10+ 动态元数据直通。详见 [Hills 调查](Hills-mpv-HDR原理与迁移评估-2026-11-10.md)。

本轮没有使用 Hills 的二进制、宿主检查或反编译代码。进一步检查发现，PiliExo 正式 mpv 已具备 gpu-next、Dolby Vision 元数据解析和 libplacebo reshape 能力；[mpv v0.41.0 EGL 辅助代码](https://github.com/mpv-player/mpv/blob/v0.41.0/video/out/opengl/egl_helpers.c) 也有 `rgb10_a2` 输出配置。因此先尝试独立 JNI 桥接加公开选项，无须预先替换 mpv 核心。此前报告中“必须重编译核心”的说法属于调查阶段方案，应以此实现验证结果为准。

## 输出与颜色处理

原生路径绕过 Flutter Texture，把既有 media-kit 播放实例接到 Hybrid Composition 中的 SurfaceView。Flutter 的弹幕、控制按钮和文本字幕仍位于视频上方。JNI 通过独立 mpv client 访问实例；Surface 引用在停止 VO 和清除 wid 后释放，避免先销毁播放实例。

使用 `vo=gpu-next`、Android OpenGL ES、`egl-output-format=rgb10_a2`、`target-prim=bt.2020`、`target-trc=pq`、10位抖动及全范围 RGB 输出。显示器报告 PQ HDR 能力后才尝试；峰值亮度使用其能力报告的整数值。

上游 Android EGL context 未提供本路径需要的色彩空间协商，因此明确设置 `target-colorspace-hint=no`，由 JNI 将对应输出窗口标为 BT2020_PQ。只有 VO 已配置、缓冲格式为 RGBA1010102 或 FP16、dataspace 设置和回读成功后，才将诊断状态标为 HDR active。格式不符、驱动改写或初始化失败时回退到现有 Media3。

[Android NativeWindow API](https://developer.android.com/ndk/reference/group/a-native-window) 的 dataspace 设置只描述缓冲颜色，不能转换像素。[mpv 手册](https://mpv.io/manual/stable/#options-target-trc) 同样要求调用者确保 HDR 信号标记。故必须配对验证目标编码、实际位深、系统合成与画面，不能只凭亮度变化判定成功。当前桥接每500ms采样一次，不等价于 Hills 在每次交换缓冲后的内部检查。

## P5 的支持范围

识别 `dvh1.05.*` / `dvhe.05.*` 时强制软件 HEVC 解码，使逐帧 RPU 及结构化元数据到达 gpu-next/libplacebo，再完成 Profile 5 的 reshape 和颜色处理。实际 track 的 Profile5 检测作为 codec 字符串缺失时的补充保护。固定样本真机输出为 `1920×1080`、`profile=5`、`hwdec=no`、`colormatrix=dolbyvision`、`gpu-next`、参数43和 `0x09c60000`。

这不实现 P5 硬件 RPU 回传。普通 MediaCodec 帧不能因为切换 gpu-next 就自动获得同等元数据；[mpv-android #1081](https://github.com/mpv-android/mpv-android/issues/1081) 讨论了相关差异。Hills 的定制 FFmpeg 行为也不能直接推广到当前正式库。4K P5 软件解码的功耗、帧率和温度仍需真机评估。

此路径输出 BT.2020/PQ RGB，不能宣称 Dolby Vision RPU、HDR10+ 或 HDR Vivid 动态元数据完整直通，也不能宣称已做仪器色准验证。

## 固定输入和参考输出

`test/fixtures/mpv_hdr/dv-p5-five-frames.mp4` 来自公开 Jellyfin 测试源的前5帧，保留 dvcC 和逐帧 RPU。固定 SHA256、提取方法及源地址在 `sample.json`。FATE 风格参考位于 `test/ref/fate/`；运行 `python tool/verify_mpv_hdr_samples.py --libplacebo`，验证 Profile5、5帧元数据、确定性软件解码校验和，以及 libplacebo 修正后的 RGB 参考点。允许 RGB 每通道3级舍入误差。

固定输入核验已通过。桌面参考不能替代 Android 候选输出验证。字幕组件固定样例验证了双行显示、更新、清空、隐藏、拖动保存和按钮响应；原生图层合成仍必须真机验证。

## 真机问题记录

- 首次候选安装遇到锁屏拒绝，用户暂用手机期间已停止所有手机操作；用户随后明确恢复 ADB 并解锁，原证书覆盖安装成功，未清数据。
- 初次实播时 `target-peak=460.0` 被 mpv 以错误码 -7 拒绝；改成整数。其他公开颜色选项已通过初始化设置。
- 初始失败回退漏传页面 onInit，Media3 已播放但页面未挂载画面和控制层；已补传。修复后真机确认画面和控制按钮恢复，Dolby Vision 4K23.976 片源仍可由 Media3 回退播放。
- 固定5帧样本每帧保留RPU和结构化元数据，桌面软件解码帧校验和及libplacebo修正RGB参考点通过。该样本仅0.083秒，短于控制层刷新节奏；真机改用保留dvcC/RPU的无损10秒循环输入后，加载遮罩消失，媒体会话持续位于 `PLAYING`。
- P5真机截图与桌面参考一致，标志从错误路径常见的绿色/青色恢复为紫蓝色；全屏与竖屏返回后，双行字幕、滚动弹幕、进度条、暂停按钮和控制层同时正常显示。暂停按钮把系统媒体会话从 `PLAYING` 切为 `PAUSED`。
- 在线 Dolby Vision 4K23.976 实测为 Profile8/HLG 输入并转成PQ输出；HDR10/PQ 4K60样本也正常。不能把这两项误记为 Profile5。
- 4K120 HDR10样本在原生重采样路径出现明显丢帧（仪表曾显示近1秒37帧、历史731帧），4K120流畅度未通过，不作为性能承诺。
- 普通arm64候选最终重新覆盖安装成功，`pm path`完整回读SHA-256与候选一致，`firstInstallTime=2026-09-02 15:19:05`保持；冷启动288ms。在线HDR样本再次进入“mpv 原生 HDR / PQ / 10-bit”。退出播放页后活动SurfaceView消失；测试后实验开关恢复关闭，ADB反向端口与本地样例服务器均已清理。

## 2026-11-10 偏灰复核

用户反馈同一 HDR 画面下 mpv 比 Media3 偏灰。复核结论：Hills 参考实现本身也只设置 BT2020/PQ dataspace，日志明确 `no HDR metadata`，没有把 mastering/MaxCLL 交给合成器；Android 公共 NDK 也没有给 GPU 渲染层提交 HDR 静态元数据的接口，Media3 的元数据来自 MediaCodec 输出格式。当前候选的两个实际偏差是固定 `target-peak=1000`（设备当前峰值为 460）以及最终普通候选使用未打 `android-egl-bt2020-pq.patch` 的正式 libmpv，EGLSurface 没有设为 BT2020/PQ。

已改为由原生读取设备 HDR 峰值，并用带 EGL PQ 补丁的 arm64 libmpv 打包候选。设备日志确认 `target-peak=460`、`format=43`、`dataspace=0x09c60000`、`android-hdr-probe=yes`、`gpu-next`；同帧 A/B 截图因手机被占用未完成，暂不宣称修复。
